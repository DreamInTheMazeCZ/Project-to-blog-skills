# Mazora 공개용 기술 콘텐츠 정책

## 검증된 사실 / 저자의 의도

- 코드는 현재 구현을 보여준다. 코드만 보고 선택 이유·개발 중 감정·시간순 시행착오를 만들어내지 않는다.
- README는 설계/목표와 당시 맥락을 보여준다. 계획과 구현은 구별한다.
- Git은 변경 사실과 날짜를 보여준다. 메시지가 없어도 당시 의도를 추정해서는 안 된다.
- 사용자 응답은 **저자가 밝힌 배경**을 보여준다. 알고리즘 성능·운영 효과의 검증 수치가 되지 않는다.
- 수치에는 출처/측정 조건이 있어야 한다. `R²`, `F1`, 시간·비용·응답률의 분모·기간·대조군·환경을 확인한다. 확인되지 않으면 삭제.

## 비공개·서술 금지

- API 키, 토큰, 내부 호스트/IP, 비밀번호, 개인정보, 고객 데이터, 실제 운영 식별자, 비공개 사업정책, 계약·보안 관련 내부 정보
- 의도적으로 남긴 임시 우회·하드코딩·기술 부채, 코드의 미해결 약점과 추측된 버그
- 확인되지 않은 '실패했다 → 개선했다' 서사, 추측된 개발 동기, 구현되지 않은 기능의 완료 주장
- 과장된 완전 자동화, 상용 운영, 무결성, 보안 인증, 성능 개선 주장
- 제3자 소스의 장문 복제; 필요한 코드는 공개 허용 범위를 확인하고 최소한으로 사용

문제를 공개 글에 일부러 언급할 필요는 없지만, 중요한 한계를 숨기기 위해 사실을 왜곡해서도 안 된다. 공개 가능한 정확한 사실만 서술할 수 없는 주제는 제외한다. 내부 메모에도 실제 비밀값은 기록하지 않고 `민감 정보 포함` 같은 설명만 남긴다.

## 문체 및 구성

- 1인칭 한국어 개발자 문체. 프로젝트의 목적, 왜 그 기능이 필요한지, 어떻게 구현되는지, 실제로 무엇이 확인되는지 설명한다.
- 독자의 입장에서 한 편에 한 가지 중심 질문을 둔다. 모든 글에 똑같은 소제목을 강제하지 않는다.
- 설계와 구현의 선택 근거는 문서·이력·저자 확인이 있는 경우만 표현한다.
- AI 상투어 반복 금지: `단순히 A를 넘어`, `핵심은 바로`, `획기적인`, `혁신적인`, `이로써 강력한`, 과도한 감탄.
- 기술 용어는 정확히 사용하고 간단한 비유보다 핵심 메커니즘을 우선한다.
- 코드 예제는 최소·핵심만 포함. 단순화한 예시는 **실제 코드 그대로가 아님**을 분명하게 표시.
- 개발 날짜와 글의 발행 날짜를 구분한다. 순서가 불명확하면 “그다음에” 같은 시계열 연결을 쓰지 않는다.
- 기존 Mazora Astro 블로그의 frontmatter와 카테고리·slug·코드 블록 규약을 **실제로 확인한 뒤** 따른다. 없는 스키마를 지어내지 않는다.

## 게시 전 체크리스트

- [ ] 제목이 독립된 기술 가치를 보여주며 다른 편과 중복되지 않는다.
- [ ] 모든 핵심 기술 주장에 A급 근거 또는 적합한 저자 진술이 연결되어 있다.
- [ ] 성능·효과 수치는 검증되었고 비교 조건을 오해하게 하지 않는다.
- [ ] 구현·계획·설계 의도를 정확히 구분했다.
- [ ] 확인되지 않은 선택 이유를 추측해 쓰지 않았다.
- [ ] 고의적 타협, 임시 우회, 내부 문제, 민감한 정보가 노출되지 않는다.
- [ ] 고객사·회사·계약·라이선스 등 외부 공개가 허용되는 범위이다.
- [ ] AI 문체와 과장, 반복 내용, 미검증 개발 연대기가 없다.
- [ ] 코드, 이미지, URL, 내부 링크, frontmatter는 확인 가능한 범위 내에서만 넣었다.
- [ ] 초안은 별도 작업 폴더에 있고 게시·푸시·배포가 발생하지 않았다.
- [ ] P0/P1 질문은 해소되었거나 관련 내용이 제거되었다.
- [ ] 최종 공개 승인은 아직 사용자에게 남아 있다.
