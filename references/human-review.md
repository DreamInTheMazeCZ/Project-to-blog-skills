# 사람의 의사결정 / 불확실성 처리 규칙

## 중요도 분류

| 등급 | 조건 | 처리 |
|---|---|---|
| P0 | 고객/개인정보/기밀 공개, 실제 성과·상용 운영 주장, 구현과 서술의 중대 모순 | 반드시 질문·답변 전까지 관련 주장 보류 또는 완전 제외 |
| P1 | 글의 중심 서사를 결정하는 설계 의도, 기술 선택 이유, 의도적 타협의 공개 여부 | 관련 파일·커밋을 근거로 사용자에게 질문, 답 전 확정 금지 |
| P2 | 사소한 코딩 방식, 작은 리팩터링 이유, 설명 가치 낮은 불명확 사항 | 기본적으로 질문하지 않고 생략 |

## 질문에 앞서 할 일

- 같은 정보가 설계 문서, 이슈, Git 이력, 테스트에 있는지 먼저 조사한다.
- 확정 가능한 구현 사실과 불명확한 개발 의도를 분리한다.
- 질문이 사실 확인인지, 개발자의 의도 확인인지, 공개 허가인지 구분한다.
- 공개 권한은 본인의 허용만으로 충분하지 않을 수 있다. 회사·고객·계약 및 제3자 권리의 허가는 사용자가 판단해야 하며 불명확하면 제외한다.

## 질문 묶음 형식

한 번에 최대 5개 질문만 출력한다. 개인 상황에 맞는 객관식 선택지와 자유 답변을 함께 허용한다. 답하지 않음/비공개를 언제나 선택할 수 있게 한다. 질문 예시:

**Q-01 [P1 / 설계 선택 근거]**
- 확인된 사실: 코드에 X 방식과 Y 라이브러리 사용이 확인됨. (근거: `src/...`, 커밋 `abc1234`)
- 확인할 내용: X를 선택한 이유가 성능, 운영 환경, 구현 비용, 다른 이유 중 무엇인지?
- 선택지: ① 성능 ② 제약 조건 ③ 빠른 구현 ④ 기타(직접 기입) ⑤ 기억나지 않음/공개하지 않음
- 이유: 3편의 핵심 기술 선택 설명에 영향을 줌
- 미응답 기본 처리: 사용 사실만 기술하고 동기는 작성하지 않음

**Q-02 [P0 / 공개 가능 범위]**
- 확인된 사실: 프로젝트에 고객 시스템 연동 코드가 존재함(민감값은 표시하지 않음)
- 확인할 내용: 고객사명·연동 인터페이스 구조 중 공개 가능한 범위는?
- 선택지: ① 익명화한 개요만 ② 특정 요소까지 허용 ③ 전체 제외 ④ 확인 후 결정
- 이유: 외부 공개와 계약상 위험
- 미응답 기본 처리: 고객 식별정보 및 연동 내부 구조 제외

답변은 사용자 의도 또는 공개 선호의 증거로 기록하고, 실제 결과의 검증자료를 대체하지 않는다.

## 사용자 답변 후 상태 갱신

- `DECISIONS.md`에 ID, 질문, 선택, 저자 설명, 공개 허용 범위, 출처(사용자 응답), 상태를 기록한다.
- 상태: `CONFIRMED`, `EXCLUDED`, `PENDING`, `CONFLICT`.
- 사용자 답이 코드·문서와 충돌하면 `CONFLICT`; 단정 대신 1회 재확인을 요청하고 미해결이면 관련 주장을 삭제한다.
- 답이 짧거나 모호하면 의미를 과잉 확장하지 않는다. 예: “속도가 중요했음”을 “응답시간 40% 단축”으로 만들지 않는다.
- 사용자 답변 없이 '가장 가능성 높은 이유'를 선정하지 않는다.

## 편집 방향의 사람 결정

다음처럼 글의 방향에 큰 차이가 나는 경우에만 독자층·공개 범위를 확인한다:
- 독자를 현업 엔지니어로 할지 비개발자로 할지
- 구현 중심 사례인지 문제 해결 중심 포트폴리오인지
- 소스 공개를 얼마나 허용할지
- 실제 회사·고객명이 드러나도 되는지

사소한 소제목·태그·연결 순서는 근거 있는 기본안을 Claude가 정하고 승인 질문을 남발하지 않는다.
